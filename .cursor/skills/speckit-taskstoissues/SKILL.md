## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding (if not empty).

## Pre-Execution Checks

**Check for extension hooks (before tasks-to-issues conversion)**:
- Check if `.specify/extensions.yml` exists in the project root.
- If it exists, read it and look for entries under the `hooks.before_taskstoissues` key
- If the YAML cannot be parsed or is invalid, skip hook checking silently and continue normally
- Filter out hooks where `enabled` is explicitly `false`. Treat hooks without an `enabled` field as enabled by default.
- For each remaining hook, do **not** attempt to interpret or evaluate hook `condition` expressions:
  - If the hook has no `condition` field, or it is null/empty, treat the hook as executable
  - If the hook defines a non-empty `condition`, skip the hook and leave condition evaluation to the HookExecutor implementation
- When constructing slash commands from hook command names, replace dots (`.`) with hyphens (`-`). For example, `speckit.git.commit` → `/speckit-git-commit`.
- For each executable hook, output the following based on its `optional` flag:
  - **Optional hook** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **Mandatory hook** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    After emitting the block above you MUST actually invoke the hook and wait for it to finish before continuing.
- If no hooks are registered or `.specify/extensions.yml` does not exist, skip silently

## Outline

### Archivist issue hierarchy (non-negotiable)

Per `AGENTS.md` and `.specify/memory/constitution.md`:

- **One epic** per spec (never one issue per `T001`, `T002`, …)
- **One sub-issue** per implementation phase or user story section in `tasks.md`
- **Tasks** (`T001`, …) are `- [ ]` checkboxes **inside** sub-issue bodies
- Write **`specs/<feature>/github-issues.md`** with all issue numbers and a **PR closing keywords** block

### Steps

1. Run `.specify/scripts/bash/check-prerequisites.sh --json --require-tasks --include-tasks` from repo root. Parse `FEATURE_DIR` (absolute path).

2. Load:
   - `FEATURE_DIR/tasks.md` — phase/story sections and task checkboxes
   - `FEATURE_DIR/spec.md` — epic title and overview
   - `.specify/memory/constitution.md` — governance (if present)

3. Verify GitHub remote:

```bash
git config --get remote.origin.url
```

> [!CAUTION]
> ONLY PROCEED IF THE REMOTE IS A GITHUB URL.

4. **Deduplication**: If `FEATURE_DIR/github-issues.md` already exists, read it. If the epic and sub-issues are already recorded and open, report and skip creation. If partially missing, create only what's missing.

5. **Parse `tasks.md` sections** — treat each `## Phase N:` heading (including user-story phases) as one sub-issue candidate. Skip non-implementation sections: `Dependencies & Execution Order`, `Parallel Opportunities`, `Implementation Strategy`, `Notes`.

   For each phase section, collect task lines matching `- [ ] TNNN` or `- [x] TNNN` until the next `##` heading. Preserve task text in checkbox form for the sub-issue body.

6. **Create epic issue** (if not already present):

```bash
gh issue create \
  --title "<type>(<scope>): <spec title from spec.md>" \
  --body "<overview from spec.md + links to spec/plan/tasks paths>"
```

Record epic number.

7. **Create sub-issues** — for each parsed phase/story section:

```bash
gh issue create \
  --parent <EPIC_NUMBER> \
  --title "<section title from tasks.md heading>" \
  --body "<section purpose from tasks.md + task checkboxes>"
```

Use the `## Phase N: …` or `## Phase N: User Story …` heading text as the sub-issue title (trimmed, max ~100 chars).

Record each sub-issue number in order.

8. **Write `FEATURE_DIR/github-issues.md`**:

```markdown
# GitHub Issues — <feature-slug>

Generated by `/speckit-taskstoissues`. Use the PR closing keywords when opening the implementation PR.

| Role | Issue | Title |
| ---- | ----- | ----- |
| Epic | #NN | … |
| Sub-issue | #NN | … |
…

## PR closing keywords

Copy into the **Issues closed** section of the implementation PR:

\`\`\`
Closes #EPIC
Closes #SUB1
Closes #SUB2
…
\`\`\`
```

Include **every** epic and sub-issue number. One `Closes #NNN` line each.

9. **Report** epic URL, sub-issue URLs, and path to `github-issues.md`.

> [!CAUTION]
> UNDER NO CIRCUMSTANCES CREATE ISSUES IN REPOSITORIES THAT DO NOT MATCH THE REMOTE URL.
> NEVER CREATE STANDALONE ISSUES FOR INDIVIDUAL TASKS (T001, T002, …).

## Post-Execution Checks

**Check for extension hooks (after tasks-to-issues conversion)**:
- Same rules as Pre-Execution Checks, but use `hooks.after_taskstoissues`
- Mandatory hooks: emit `EXECUTE_COMMAND:` and run them before finishing

## Done When

- [ ] Epic issue exists and is linked as parent of all sub-issues
- [ ] One sub-issue per phase/user story in `tasks.md` (tasks as checkboxes in bodies)
- [ ] `github-issues.md` written with complete table and PR closing keywords block
- [ ] No standalone issues created for individual `TNNN` tasks
