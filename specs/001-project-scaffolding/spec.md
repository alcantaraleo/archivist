## 1. Motivation

Archivist currently has no runnable codebase. Before any domain capability can be implemented or tested, the project requires a complete structural foundation: a Gradle multi-module build, the four Clean Architecture layers as separate modules, the root package hierarchy, and the minimum wiring needed to confirm each layer can compile and depend on each other in the correct direction.

Without this scaffold, no feature specification can proceed to implementation. This is the enabling foundation for all future work.

---

## 2. Responsibilities

### What this scaffold delivers

- A Gradle multi-module project with Kotlin DSL (`build.gradle.kts`) at all levels
- Four modules mapping to the four Clean Architecture layers: `domain`, `application`, `infrastructure`, `transport`
- Root package hierarchy `io.archivist` established in each module
- Dependency declarations between modules enforcing the permitted import rules
- A runnable Spring Boot application entry point in the `transport` module
- Placeholder source files in each module confirming the package structure compiles
- A `settings.gradle.kts` including all four modules
- Dependency version management centralised via a Gradle version catalogue (`gradle/libs.versions.toml`)
- An externally-injected configuration pattern: all environment-specific values (Second Brain root path, future database URLs, API keys, etc.) are supplied via environment variables and mapped through Spring Boot's `application.properties` — no value is hardcoded in source code

### What this scaffold does not do

- Does not implement any domain capability (`retrieveContext`, `findDecisions`, etc.)
- Does not connect to any Second Brain data source
- Does not expose any MCP tool or REST endpoint with real behaviour
- Does not include retrieval logic of any kind
- Does not include application-layer use cases with real logic

---

## 3. Public Contract

This specification does not introduce a domain capability. It establishes the structural precondition for all capabilities. There is no `port.in` interface to define here.

The deliverable is a compilable, testable project skeleton with verified inter-module dependency rules.

---

## 4. Acceptance Criteria

1. `./gradlew build` completes without errors from the repository root
2. The project contains exactly four Gradle submodules: `domain`, `application`, `infrastructure`, `transport`
3. Each module contains at least one compilable Java source file under the `io.archivist` root package
4. The `domain` module declares no compile-time dependency on Spring Boot, Spring AI, MCP SDK, `application`, `infrastructure`, or `transport`
5. The `application` module declares a compile-time dependency on `domain` only; no Spring Boot, MCP SDK, `infrastructure`, or `transport` imports
6. The `infrastructure` module declares dependencies on `domain`, `application`, Spring Boot, and Spring AI; it does not depend on `transport`
7. The `transport` module declares dependencies on `application`, Spring Boot, and the MCP SDK; it does not depend on `infrastructure` directly
8. A Spring Boot application starts successfully from the `transport` module; `./gradlew :transport:bootRun` (with required env vars set) logs `Started ArchivistApplication` and remains running in STDIO mode
9. `./gradlew test` executes without failures (placeholder tests are acceptable; zero tests is acceptable)
10. No star imports exist in any source file generated by this scaffold
11. No field injection (`@Autowired` on fields) exists in any source file generated by this scaffold
12. No environment-specific value (file paths, URLs, credentials, ports) is hardcoded in any source file or `application.properties`; all such values are read from environment variables
13. `application.properties` uses Spring Boot's `${ENV_VAR_NAME}` placeholder syntax to bind environment variables; a documented list of required environment variables exists in `README.md` or equivalent
14. Starting the application with any required environment variable absent or empty causes an immediate startup failure with a descriptive error message identifying the missing variable — the service must not reach a running state with incomplete configuration

## 5. Domain Model Impact

This specification introduces no new domain types. It establishes the package locations where future domain types will live:

- `io.archivist.domain.model` — to receive `Evidence`, `Provenance`, `Query`, `KnowledgeType`, `KnowledgeZone`
- `io.archivist.domain.port.in` — to receive public capability interfaces
- `io.archivist.domain.port.out` — to receive retrieval gateway interfaces
- `io.archivist.application.usecase` — to receive use case interactors
- `io.archivist.infrastructure` — to receive retrieval strategies and Second Brain adapters
- `io.archivist.transport.mcp` — to receive the MCP adapter

## 6. Architectural Impact

### Module structure

```
archivist/                         ← root project
├── settings.gradle.kts
├── build.gradle.kts               ← version management, shared config
├── domain/
│   └── build.gradle.kts           ← no Spring, no MCP
├── application/
│   └── build.gradle.kts           ← depends on :domain
├── infrastructure/
│   └── build.gradle.kts           ← depends on :domain, :application, spring-boot, spring-ai
└── transport/
    └── build.gradle.kts           ← depends on :application, spring-boot, mcp-sdk; bootJar here
```

### port.in (public capability)

None introduced by this specification.

### port.out (retrieval gateway)

None introduced by this specification.

### application (use case)

None introduced by this specification.

### infrastructure (retrieval strategy)

None introduced by this specification.

### transport (MCP)

The `transport` module hosts the Spring Boot `@SpringBootApplication` entry point. No MCP tools are registered by this scaffold.

### Configuration pattern

All externally-injected values are centralised in an `ArchivistProperties` configuration class (annotated `@ConfigurationProperties`) in the `transport` module, alongside `ArchivistApplication`. Configuration binding is a Spring Boot wiring concern, not an infrastructure concern — it belongs at the application entry point, not in the retrieval layer.

Infrastructure adapters that need configuration values receive them as plain constructor parameters (e.g., `String`, `java.nio.file.Path`) injected by Spring. They never import `ArchivistProperties` directly and never read environment variables or system properties themselves.

Example variables established by this scaffold:

| Environment Variable          | Description                                      | Required                                     |
| ----------------------------- | ------------------------------------------------ | -------------------------------------------- |
| `ARCHIVIST_SECOND_BRAIN_PATH` | Absolute path to the Second Brain root directory | Yes — absence causes startup failure (AC-14) |

Additional variables are added here as each capability spec introduces new infrastructure dependencies.

## 7. Out of Scope

- Any domain capability implementation (`retrieveContext`, `findDecisions`, etc.)
- Second Brain connectivity or file reading
- MCP tool registration or wiring
- Embedding or vector store configuration
- Any retrieval strategy (lexical, BM25, hybrid)
- ArchUnit dependency enforcement tests (can be introduced in a follow-up)
- Docker or container configuration
- CI/CD pipeline configuration

## 8. Open Questions

- [x] Which Spring Boot version to pin? → **Spring Boot 4.1.0** (see research.md)
- [x] Which Spring AI version to pin? → **Spring AI 2.0.0** (see research.md)
- [x] Should a Gradle version catalogue (`libs.versions.toml`) be used from the start? → **Yes** (see research.md)
- [x] Should missing required environment variables fail fast at startup or be deferred until first use? → **Fail fast at startup.** If any required configuration is absent, the service must not start. Silent failures or deferred null errors are never acceptable.
